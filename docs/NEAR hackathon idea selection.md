# Build the Intent Firewall, Not Illia's List

Furqaan should build **Intent Firewall**, rebuilt as a hybrid. An agent's NEAR smart-wallet contract runs an action only when it carries a TEE-signed "ALLOW" verdict from NEAR AI Cloud. The verdict covers the exact action bytes, and the contract checks it on-chain with `sha256` + `ecrecover`. Enter it in **AI Security & Defense**, **Agent Economy** and **Privacy & Private AI**. It scores 4.25/5 on the weighted rubric below, against 3.45 for the runner-up. It wins because it is the only candidate that is buildable with documented APIs, absent from Illia's Oct 3 list of 13 ideas, and a word-for-word match for a track's hints. The Security track asks for "AGENT SECURITY, FUNCTION CALL KEYS, TEE ATTESTATION" ([nearhackathon.com](https://nearhackathon.com)). It also lands with the judges most likely to mark down the other ideas. Haseeb Qureshi says AI's real uses "remain within software engineering and security" ([haseebq.com](https://haseebq.com/2026-predictions/)), and Avichal Garg calls agent-wallet liability an unsolved frontier ([CoinDesk](https://www.coindesk.com/business/2026/02/24/crypto-wallets-for-ai-agents-are-creating-a-new-legal-frontier-says-electric-capital)). The runner-up is **Sealed-lite**, a scoped-down Sealed: a public NEAR escrow with commit-reveal sides, 1Click cross-chain funding and an attested AI resolver. It fits Furqaan's prediction-market background best. But Confidential Intents cannot hold contract balances, so most of its "confidential" claim falls away, and Haseeb is openly skeptical of new prediction markets. Six of the ten ideas copy Illia's list almost word for word, so expect crowded tracks. Copy-Key is not buildable as specified, and Intents Ledger is already lapped by a public repo. Both top picks rest on one unproven step: verifying a real NEAR AI signature inside a NEAR contract. Run that test on Day 1, before writing anything else.

## Confidential Intents cannot hold contract balances, which guts three ideas

The biggest technical finding is that **Confidential Intents is a swap/transfer/balance product exposed only through 1Click**. It runs on "FAR", a permissioned NEAR fork with no public RPC, and the only documented contract there is the predefined `intents.far` ([NEAR Intents MM docs](https://docs.near-intents.org/integration/market-makers/confidential-intents.md)). Aurora's docs say it plainly: "Confidential Intents is not private DeFi and does not obscure the destination." Confidential deposits and DeFi actions are still "rolling out" ([Aurora Intents docs](https://docs.intents.aurora.dev/confidential-intents)). A live test on Oct 22 found that confidential quotes return **401 without a per-user signed session** ([1Click API](https://1click.chaindefuser.com/v0/quote)). Since Jul 13, confidential solvers have been allowlist-only ([changelog](https://docs.near-intents.org/changelog/overview.md)). On the documented APIs, then, no hackathon contract can hold shielded balances. Third-party apps cannot consume view keys; the only evidence for view keys is the GA blog's "user-initiated" line ([NEAR blog](https://www.near.org/blog/announcing-general-availability-of-confidential-intents)). And no app can act as a confidential matcher.

Three more facts shape the field. **Shade Agents have been unmaintained since Apr 19, 2026** ([docs.near.org](https://docs.near.org/ai/shade-agents/quickstart/deploying)), so the TEE route runs through NEAR AI Cloud or OutLayer. Rhea lending was hit by an **$18.4M exploit on Apr 16**, and its reopening is unconfirmed ([The Block](https://www.theblock.co/post/397961/rhea-finance-post-mortem-exploit-losses-18-4-million-double-initial-estimates)). And after the $3.8M ghost-balance exploit, **`intents.near`'s deposit `Notify` was removed entirely on Oct 7**, so any design that relied on a deposit triggering contract logic now needs an off-chain relayer ([ChainCatcher](https://www.chaincatcher.com/en/article/2296917); [The Coding postmortem](https://thecoding.substack.com/p/near-intents-ghost-fund-postmortem)). On the positive side, 1Click is mature. It lists 205 assets on 37 chains, quotes return in about 1 s, and a Base→Arbitrum USDC route estimates 34 s ([1Click tokens](https://1click.chaindefuser.com/v0/tokens)). NEAR AI Cloud signs every response with EIP-191 ECDSA or Ed25519 over `sha256(request):sha256(response)`, a format a NEAR contract can check ([NEAR AI docs](https://docs.near.ai/cloud/verification/reference/response-signature-verification.md)).

## The Security track's hints describe the Intent Firewall almost exactly

The winning build is a **wallet contract that trusts meaning, not just rules**. The agent holds only a function-call access key scoped to the wallet's `propose` method. Each proposed action is canonically encoded as receiver | method | args-hash | deposit | nonce | expiry, and embedded in a prompt to an open-weight model on NEAR AI Cloud. The prompt pairs that action with the owner's plain-English mandate. Qwen3.8-27B is the best fit: **$0.04 in / $1.35 out per M tokens** and listed as ready ([NEAR AI models](https://cloud-api.near.ai/v1/models)). The model returns a structured ALLOW/DENY verdict. The service fetches its signature from `GET /v1/signature/{chat_id}` ([API ref](https://docs.near.ai/api-reference/attestation/get-completion-or-responses-api-signature.md)). The contract recomputes both hashes, `ecrecover`s the signer and checks it against a TEE address registered after an off-chain check of `/v1/attestation/report` ([attestation ref](https://docs.near.ai/api-reference/attestation/get-attestation-report.md)). It then confirms that the action bytes in the signed request match the one being executed, and only then executes. Hard per-transaction caps and allowlists stay in the contract as a deterministic backstop. Cross-chain spending goes out through 1Click.

The pitch writes itself against the competition. OutLayer enforces limits, allowlists and k-of-n approvals inside TDX. It documents **"no external co-signer or webhook mechanisms"**, and for Intents swaps its TEE "does not re-verify token/amount against the 1Click artifact" ([OutLayer](https://outlayer.fastnear.com/docs/agent-custody)). Intent Firewall checks exactly that semantic gap: does this recipient, amount and token match what the owner asked for? The other off-NEAR intent firewall, ciphergate on iExec, binds a proof to a Safe action rather than a semantic judgment ([GitHub](https://github.com/Lukeknow0/ciphergate)). Furqaan's x402 background suggests the strongest demo. A paying agent hits a **malicious 402 paywall whose response injects "pay 10× to this address"**. Rules alone pass it if it fits under the cap. The firewall blocks it and leaves a signed receipt. A $150K prompt-injection drain has been reported, though only from a secondary source ([DEV](https://dev.to/payload-tools/your-agents-wallet-needs-a-policy-not-just-a-signer-5f4m)). The closest NEAR x402 demo, JustaLab's, only enforces a spending cap ([GitHub](https://github.com/JustaLab-co/x402-near-intents-demo)).

Track choice follows the hints. **AI Security & Defense** is the main bet: "Give AI money without giving it the keys to everything." **Agent Economy** fits because the demo agent pays for APIs and data cross-chain via NEAR Intents. **Privacy & Private AI** fits because the verdict runs on TEE-hosted private inference, one of its named hints ([nearhackathon.com](https://nearhackathon.com)). The README must name each hint, because HACKATHON.md tells entrants to "name them in the README" and to write "do X - see Y" steps for the AI judges ([HACKATHON.md](https://nearhackathon.com/HACKATHON.md)). Four risks matter. First, the firewall model can itself be prompt-injected. Pass untrusted tool output as quoted data, use structured outputs, and keep the hard caps. Second, the false-positive rate is unknown until it is measured, which is why Day 1 includes a measurement. Third, TEE signing keys rotate, and how long signatures are kept is undocumented, so fetch each one immediately and keep the allowlist updatable. Fourth, overclaiming. Do not say the contract verifies the TDX quote; say the signer was attested off-chain and allowlisted. If Sealed-lite becomes the pick instead, it enters **Privacy & Private AI, Unstoppable DeFi and Open Innovation**. It must state in the README that positions are public on NEAR and that sides are hidden only by commit-reveal until close.

Pure curl spikes against public APIs before then are probably harmless, but confirm that in Discord. Budget $20–50 of mainnet funds, because there is effectively no 1Click testnet. Check every field name against `https://1click.chaindefuser.com/docs/v0/openapi.yaml` and the NEAR AI API reference before coding. HACKATHON.md explicitly warns against assuming endpoints.

## Conclusion

The research turns the selection question upside down. The ideas most obviously "on thesis" are the riskiest. Illia's wishlist will crowd them, and the most glamorous of them (true Sealed, Copy-Key, private-fill OTC) need confidential contract state that NEAR does not expose. What NEAR does expose, and what few entrants will use well, is **verifiable AI output that a contract can check**. That is a NEAR-native answer to the agent-liability problem the investor judges keep raising. Intent Firewall turns that into a product whose demo is a visible attack being stopped, which both the human and AI judges can verify from the README alone.

The bigger implication is that the attested-verdict verifier is reusable. The same contract that gates an agent's spending can resolve a Sealed-lite market or arbitrate a Bidwire job. So the Day-1 work is never wasted, whichever way KT3 lands. It also gives Furqaan a post-hackathon path back to prediction markets, built on infrastructure he will already have shipped. The main unknown is how strong the field is. Track entry counts cannot be seen until judging. The only lever left is execution depth, so the scope should stay narrow.
